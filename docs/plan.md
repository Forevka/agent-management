# Agent Fleet: plan

## Context

The goal is to manage a fleet of Claude Code agents from one Telegram group.

- One host (the VPS) is the **orchestrator**.
- Every other host (Windows PCs, and the VPS too) runs a **node**.
- Nodes and the orchestrator talk over **iroh**, an encrypted two-way peer-to-peer link.

You send requests in Telegram. The orchestrator:

- works out which project a request belongs to;
- hands it to a suitable agent, or creates a new one. Each agent has its own Telegram bot identity.

That agent then:

- writes a plan;
- gets the plan approved through a web page;
- does the work and reports progress as a checklist in its own topic.

Two kinds of things also flow into Telegram:

- Slack messages are mirrored into project feed topics, where agents can see them.
- A **secretary** session reads every message from every conversation the owner is in, keeps the owner's todo list and escalates to the brain.
- Anything that needs your input goes to per-project "needs you" and "FYI" topics.

The fleet remembers projects and tasks over time through **Hindsight**, one self-hosted memory server shared by the orchestrator and all agents.

This is a new project, unrelated to `stoneshard-mod`. It goes in **`Forevka/agent-management`**, cloned into this session.

## Decisions (from the interview)

| Area | Decision |
|---|---|
| Scale | Large: 10+ hosts, dozens of agents. **Postgres** (with pgvector, which Hindsight also uses). |
| Hosts | Windows PCs run a Windows service; the Linux VPS runs the orchestrator and a node. |
| Users | Only you: a Telegram user-ID allowlist. Every other user is ignored. |
| Claude per node | Configured per node: (1) the **start command** (path and extra args), (2) **auth**: either the login Claude already has (subscription) or a **token** you set (`CLAUDE_CODE_OAUTH_TOKEN` / `ANTHROPIC_API_KEY`). Scaling up means adding nodes and accounts. |
| Permissions | `--permission-mode auto`. The brief tells the agent to create its own git worktree. When it needs you, the question goes to the human queue. |
| Isolation | A git worktree only. No Docker. |
| Model | Opus by default (`FLEET_MODEL`), with **per-agent defaults and per-task overrides** of the model and of Claude's effort level (low, medium, high, xhigh, max): a task runs with its own model and effort, else its agent's (set by the owner on the web Agents page, or proposed by the brain with `admin agent-set` for the owner's approval), else the fleet's model and Claude's default effort. The brain chooses per task (`create-task --model --effort`) and proposes agent defaults only within the owner's allow-list (`FLEET_ALLOWED_MODELS`, `FLEET_ALLOWED_EFFORTS`; unset: `FLEET_MODEL`, sonnet and haiku, and low, medium and high, so the costlier models and efforts are opt-in; set but empty allows nothing): a cheap model and low effort for small chores, a strong model and high effort for hard design, debugging or risky changes, otherwise nothing. A node whose Claude command sets `--model` or `--effort` keeps its own (for effort the orchestrator leaves its value out: which of two `--effort` flags Claude takes is not something to rely on). The task's opening message, its web page and `fleet agent tasks` show what it runs with. Except the secretary: **Haiku** by default (`FLEET_SECRETARY_MODEL`), since it reads every message. |
| Request flow | "do X" → orchestrator finds the project → sends it to the agent that did similar work, or creates a new agent from the bot pool → that agent plans in **plan mode** → plan page on the VPS (answer its questions, approve) → work → later questions come as Telegram buttons or free-text replies. |
| Deploy | **A merge to `main` is a deploy**, so the owner's merge is the one gate. CI on a green `main` tags the commit with the next patch version and publishes a release (binaries with SHA-256 sums); every binary reports its release (`fleet --version`, `nodes.app_version`). On the VPS a root timer rolls the release out — only a tag on `main`, so a pushed tag cannot bypass the merge: build the tag's image, **dry-run its migrations against the live database in a rolled-back transaction** (a fresh test database cannot show a backfill meeting real rows — that took production down once; the dry run waits at most 5 s for a lock, so it never stalls the live orchestrator), back up, swap, require 20 s of continuous health, roll back otherwise and health-check the rollback too; then this host's node, once idle or after two hours. **Rolling back works because the migrator ignores applied migrations it does not know and every new column is nullable or defaulted**, so the previous release starts against the newer schema and can still write to it. A failed release is not retried; the next one is. The updater is root code and the one thing that does not update itself: a change to it is installed by a person after reading it. **Windows nodes follow by themselves**: on connect, a node behind the orchestrator's release is told which one to move to (`UpdateAvailable` — added without a protocol bump and sent only to releases after v0.2.3, which can read it, so no node already out there lost its link; across a future bump a refused node finds the same in its refusal). Only under the launcher, which opts in and can roll back: the node downloads the release from the GitHub repository its own binary was built for (fixed at build time, never named by the orchestrator, so a compromised orchestrator cannot hand nodes a binary of its choosing — at most another published release, through a refusal's hint, which may move a node back), refuses it unless it matches `SHA256SUMS` and reports that version, retries with backoff while the release's files are still being published, waits for its agents (two hours, a day while one waits on the owner), swaps itself and exits. The launcher restores the previous binary if the new one keeps dying at startup (and records that release as rejected, so it is not taken again) or never connects (not recorded: the machine may have been offline). The trust is GitHub's release, which only CI on `main` publishes. Linux nodes outside the VPS are updated by hand. |
| Task keys | Every task has a short fleet-wide handle, **`F-41`**, beside its long id (`bioins-BIOINS-5068`). The owner names a task by it — "take F-41 into work", "stop F-39" — and it is accepted everywhere an id is: the brain's tools, a topic, `/tasks/F-41`. One letter on purpose: it is **the fleet's own namespace, never an external tracker's**, and the orchestrator refuses to start if any project's Jira key would answer to the same prefix, so one key means exactly one thing. Assigned by a column default, so no task can be created without one; the fleet's own standing sessions have none, being work for nobody. |
| External tickets | A task says what it is about **outside** the fleet: the Jira ticket it came from (linked automatically from the ticket it was created with), the merge request it opened, a pull request, a page. The agent records its own — `fleet agent link !940` the moment it opens one — because the number is discovered during the work and nobody else knows it; the brain and the owner can link too, and the owner can unlink on the task page. Shown as chips on the board card, resolved to a URL where the fleet knows the host (Jira, from the project's own site). A link is a **claim, not a capability**: recording `BIOINS-5068` grants nobody access to it, and whether an agent may read that ticket is still `jira`'s decision. |
| Agents | **Persistent specialists**, each pinned to one project. Their Claude `session_id`s are stored so follow-up work (e.g. client feedback) resumes the same session. |
| Parallel work | **One agent runs one session at a time** (the node would otherwise kill the running one), so a project with one specialist does its tasks strictly one after another. When a task would have to wait and a node still has a free slot, the orchestrator gives the project **another agent of the same role** instead of queueing it — named after the first (`bioins-dev`, then `bioins-dev 2`) — up to `FLEET_MAX_AGENTS_PER_PROJECT` (default 3) per role, so a project may still have an implementor, a reviewer and a tester. The task's topic says who took it, since its brief named the agent it had then. Two things never move: a task that has already opened a session stays with the agent that opened it (resuming someone else's transcript would hand an agent another name's work), and the fleet's own standing sessions are one of a kind. Each extra agent is another concurrent Claude session on the same account, which is the real reason there is a cap. |
| Disk space on nodes | Claude Code keeps every session, subagent and transcript under `~/.claude`; on a full disk it fails mid-run, cuts the transcript short (a resume then loses context), and every task placed there fails after it. So each node reports free space (`Body::DiskReport`) when the orchestrator asks on connect (`Body::DiskReportWanted`, sent only to v0.2.4 and later, so no older node or older orchestrator ever sees a message it cannot decode — no protocol bump), every 5 minutes and when its mappings change: one entry per volume holding Claude Code's config dir or a mapped project, plus the five biggest folders under `~/.claude/projects`. The node only measures; the orchestrator decides. Below `FLEET_DISK_LOW_GB` (default 5) the owner is told once, with sound and with where the space went; below `FLEET_DISK_FLOOR_GB` (default 1) **new task runs on that node are held** — they wait in the queue with a note saying it is the disk — until a report shows space again, when they start and the owner is told quietly. Only a change of state is told — and a warning as bad as one already sounded in the last 12 hours comes silently — and a volume leaves a state only with 10% more than its threshold (judged per volume), so a disk at the line does not flap. While a node is `full`, each report retries the queued work, since one disk may be freed while another keeps it `full`. A report older than 20 minutes holds nothing (a node whose measuring hangs on a dead network drive must not hold its work for good, and housekeeping then looks at the queue again), and a report that measured nothing changes nothing. A run is held only if the full disk is one it writes to (Claude Code's, or its project's); runs already going are left alone; **the fleet's own sessions are never held**, so the owner can still reach the fleet while freeing space. Absolute sizes, not percentages: 5% of a 2 TB disk is 100 GB free. Shown in `/nodes`, on a node's page, in `/status` and in the brain's `admin show node(s)`. Freeing space stays the owner's job for now (no automatic pruning of transcripts). |
| Bot pool | You make bots with BotFather and register their tokens; the orchestrator assigns them and renames them (`setMyName`/`setMyDescription`). It never blocks on them: **an agent with no bot works and speaks as the orchestrator**, so a task is never refused because the pool is empty. When that happens the orchestrator asks for one more bot the way Telegram allows a bot to ask — a `request_managed_bot` button in your private chat, which opens Telegram's own creation flow pre-filled with the agent's name and username, hands the fleet the new bot to manage, and lets it read the token itself (`getManagedBotToken`). You tap once and never see a token; the bot then goes to the agent you were asked about. At most one ask a day, because a refusal usually means your account is at Telegram's own cap on bots it may own. A bot cannot create a bot (`bots.createBot` is user-only), so the tap is structurally required, not a convenience. |
| Telegram output | A plan link, then a **milestone checklist** that gets ticked off, then a short summary. No tool calls and no reasoning text. A step the work did not need is **skipped** (`fleet agent skip <n> --reason …`) and shown as ➖ struck through, with the reason; the header counts done out of all steps and mentions the skipped ones ("Milestones · 2/3 · 1 skipped"). Completing a task shows any step still open as skipped, so a finished checklist never shows ☐. |
| Notification sound | Decided per message kind (`chat::Notify`), never per call site. **With sound**: what needs the owner (plans, questions, permission requests, `ask` in "needs you", admin proposals, reminders, login links the brain sends) and how a task ended (done, failed, stopped, could not start), and the brain's replies in General. A session ending is silent when the owner stopped the task. **Silent**: task briefs, checklists and their edits, progress posts (`fleet agent post`, unless `--notify`, and then at most one loud post per task per 10 minutes), queue and "waiting for a node" notes, pointers in task topics, FYI items, Slack mirrors, and confirmations of what the owner just did. |
| Feedback while working | An owner message for the brain (General) or for a task's agent (its topic) gets a 👀 reaction at once, and "typing…" shows in that topic, renewed every few seconds, until the agent has answered: every message handed to a run gets its own turn and `result` (a message sent mid-turn is queued for the next turn, checked against the real CLI), so it stops when every message has its `result`, the agent replies, it waits on the owner (a plan, question or permission), or its run ends or is lost; at most 10 minutes. A message only queued (no node can take it now), or sent while the agent waits on the owner, gets its 👀 but no typing. In task topics it comes from the task's agent bot. Typing only uses rate-limit room that is free at that moment and backs off on 429s. Best effort: it never delays delivery. |
| Item copies | A plan or question shows twice, with the same buttons: the card in "<project> · needs you" and a pointer in the task's topic. Every copy is recorded, and answering anywhere (a button on either copy, the web page, a typed reply to either) updates all of them to the outcome and removes the buttons. Items cancelled because their run ended, their node restarted or was revoked are retired the same way, and a copy recorded after its item was already settled is updated at once. A typed reply to a permission prompt denies it, passing the text to the agent. |
| Topics | One per task, named `{proj}-{ticket}`. Per project there are also `{proj} · needs you` and `{proj} · fyi`, plus a feed topic for each mapped Slack channel. Three standing topics belong to the fleet itself, each created on first use and remembered in `kv` (`topics.rs`): **📋 Inbox** is only for third parties reaching the owner (the secretary's todos, its answers and the daily digest, reply drafts, and what it passed to the orchestrator about those messages); **🤖 agent-communication** is the fleet talking to itself (the brain's relayed notes to the secretary, agents' messages to each other), readable but never demanding; **📜 Rules** is the log of the secretary's triage rules, so they are searchable in one place. Typed messages in agent-communication and Rules are ignored: they are read-only logs. A task's own topic stays that agent's work, and General stays what needs the owner. |
| Ticket IDs | The tracker key if there is one (e.g. Jira `ABC-123`), otherwise an auto number per project. |
| Agent-to-agent | Only through the orchestrator. No native Telegram bot-to-bot messages. |
| Roles at launch | Implementor, Reviewer, Tester. |
| Projects | Registered by hand. A project is created once on the server (its configs and secrets), and each node maps a local folder to it. |
| Git, PRs, rules | Each project's `AGENTS.md`/`CLAUDE.md` sets the rules. When the agent is unsure, it asks you through the human queue. |
| Secrets | A free-form secrets manager on the server: folders of key/value pairs, with presets such as Jira. At spawn time the node writes a `.env` file **outside the project**. The brief says how to read a single key (`fleet secret get` / your skills' scripts) so the whole file never lands in the transcript. |
| Feeds | Slack first, behind an adapter interface so other sources can be added later. Each Slack channel can map to a project feed topic. **Reversed decision:** at first only the owner's user token was available, so the adapter only **polled** mapped channels. The owner now has a Slack app and chose **real-time intake of every conversation they are in** (DMs, group DMs, private and public channels) through **Socket Mode** with user-scoped event subscriptions, so the secretary sees everything and "what did I miss" summaries are possible without listing channels one by one. With only the user token configured, the old polling of mapped channels still works. Gaps while disconnected are backfilled from history. The adapter details live in `crates/feeds`; everything above it is source-agnostic (`Incoming`: source, conversation id/name/kind, author, thread, text, subject, link, mentions of the owner), and message refs are opaque `<source>:<conversation>:<message>`. **Google Chat is the second adapter** (a `gchat` secrets folder: `GOOGLE_CLIENT_ID`/`_SECRET`/`GOOGLE_REFRESH_TOKEN`, an owner "authorized user" OAuth credential): polling only (there is no Socket-Mode equivalent), about every 30 s, of every space the owner is a member of, no history import on first start, and no notification/mute settings exposed by the API (an owner rule stands in). The orchestrator runs every configured source on its own task with its own cursor, restarting one when its settings change and telling the owner once if it stops for good; each source's messages carry a label showing where they came from (`Slack · #channel · name`, `Google Chat · space · name`), shown wherever the secretary cites a message (todos, escalation notes, digest citations, reply drafts) and on `/inbox`. Unmapped conversations are not mirrored raw to Telegram; the secretary handles them. Gmail later needs only an adapter, a config entry and docs. The orchestrator runs each source and stores what it delivers; a message that cannot be stored is retried before anything newer, and the source's checkpoint is saved only once everything before it is stored. A source that stops with an error (a revoked or wrong token) is reported in General and stays stopped until its settings change. A message the database refuses for good (a value or constraint error) is logged, audited and skipped rather than holding up the rest; NUL characters are dropped on the way in; mirroring and triage notes are best effort; a repeat of a stored message changes nothing; and the source is not started until its saved cursor could be read. Agents only read Slack. The orchestrator can **propose tasks** and **propose replies**. An approved reply goes out through `chat.postMessage` with your token, so it **appears as you**. Approval is therefore always required, and the proposal shows the exact text. |
| Unanswered questions | Reminders only. Agents never answer on your behalf. |
| Memory | **One** Hindsight instance on the VPS for all agents and the orchestrator, internal to the Compose network. Agents use it through `fleet agent memory ...`, which the orchestrator forwards. Each agent gets its own bank prefix (`agent-<id>`, plus any `agent-<id>--<name>`); a project's agents share `project-<slug>`; the brain may use any bank. Nodes need no Hindsight URL or key. Its internal LLM is **Haiku via an Anthropic API key**. **Memory builds up without the agents remembering to save it:** when a task completes (once per finish), the orchestrator saves the task id, title, agent and its (redacted) completion summary, clipped to ~4 KB, to the project's shared bank with context `task completion`; when an agent session dies before completing (status failed), it saves how far the checklist got, as `task failure`. Not for stopped tasks or the fleet's own sessions; in the background, best effort, never holding up or failing `complete`. Agents still retain what goes beyond the summary (decisions and why, conventions, gotchas). |
| Orchestrator brain | A long-lived Claude Code session on the VPS node. Like every agent, it acts through `fleet agent ...` commands, with extra orchestration commands. |
| Secretary | A second long-lived session (task and agent `secretary`, in the brain's project and so on its node; like the brain it takes no agent slot on its node), on Haiku. It gets every message the owner receives, except channels marked triage (the brain still sees those) and the owner's own messages (context only), in **batches**: messages to the owner personally (direct, group, a mention) after a ~30 s debounce, other traffic every 10 minutes or 50 messages, at most 80 shown per batch (channel traffic beyond that is counted per conversation and readable with `feed read`; personal messages wait for the next batch), and at most 30 batches an hour (`FLEET_SECRETARY_*`). A batch is marked handed over only after it was delivered, so a failure repeats it rather than losing it; a batch carries at most ~50 KB of messages; while a text waits for the secretary (its node away, its run not preparable), no further batch is built (the messages stay pending), and when it starts, its first turn takes every waiting text from the owner or the orchestrator and as many batches, newest first, as fit in ~60 KB (older whole batches are left out, with a note; nothing is cut). The fleet's own sessions (brain, secretary) stuck that way with texts waiting (failed, queued, or stopped by a reset) are retried after 5 minutes, backing off to 30 (the backoff ends only when a run reports that it started), and sooner after the owner changes a node's settings or a node's projects change (not on every reconnect), though never within a minute of the last start. Each reason they cannot run (could not prepare, could not start on the node, waiting for a node) is told to the owner once per episode (since the session last produced output, or the owner last changed the settings of a node with its project, so a fix that fails again is told), keyed on the reason without run-specific paths and ids, while a run started by the owner's own message is always told the current reason; ordinary tasks keep their once-per-wait note. Each batch is framed untrusted, one JSON line per message with its ref, and lists the owner's rules as JSON strings with who added them. An edit of a message already triaged keeps the text the secretary saw and stores the new one beside it; a message deleted at its source is forgotten. When the source reports how much attention the owner gives a conversation (muted, mentions only), it is stored per conversation, shown on each batch line (`attention`) and as a badge on `/inbox`: muted messages never count toward the 50 that hurry a batch, and the secretary treats them, and conversations an owner rule calls muted, as low priority (a todo or escalation only for a mention or something unmistakably urgent for the owner; mentions-only conversations only for mentions or direct asks). **Autonomy: triage, todos and escalation only.** It decides per message: ignore, note (for summaries), **todo** (posted silently to the Inbox topic with ✅ Done / 🗑 Dismiss / 🛠 Make task) or **escalate** (a framed summary plus refs to the brain, at most `FLEET_SECRETARY_ESCALATIONS_PER_HOUR`, default 10; beyond that it adds a todo). It cannot create tasks, reply anywhere, message agents (nor they it) or administer the fleet: those tools are refused by its IPC identity and its skill omits them. Its memory stays in its own banks (`agent-secretary`, `agent-secretary--*`), never a project's shared one. It gets no secrets, and its Claude session is locked down (verified against the real CLI 2.1.268): `--tools Bash,Skill` (no Read, Glob, web or sub-agent tools), `--setting-sources ""` (no settings files), `--strict-mcp-config` (only the fleet's permission hook), `--permission-mode dontAsk` with only `Bash(fleet agent:*)` allowed, so anything else (`$(...)`, `VAR=... fleet agent`, network, writes, reads outside its directory) is refused without asking anyone, and the permission hook denies the secretary anything that reaches it. It runs in an empty working directory of its own on the node, so the read-only commands Claude allows by itself see nothing. A node whose Claude command carries flags that would widen this (`--dangerously-skip-permissions`, `--add-dir`, `--permission-mode`, `--allowedTools`, `--settings`, `--tools`, `--mcp-config`, `--plugin-dir`, ...) is refused for it. **Make task** passes the todo to the brain as the owner's request (trusted: the owner tapped it), with the todo's wording framed as data; the todo becomes "task requested" and nobody changes it afterwards. **Replying:** the owner may reply to a secretary post that cites source messages (a todo, or an escalation note or digest, whose cited refs are kept in `inbox_refs` keyed by that post's Telegram message) with an instruction ("tell her Friday works"); that reply is the secretary's own turn, with the cited messages attached as context. `reply_draft` works only on that turn (a third-party message can never start one) and posts a card to the Inbox with **Send / Edit / Cancel**: Send posts the drafted text, as the owner, through the source's own reply handle (in its thread when it has one); replying to the card with new text replaces the draft, word for word; nothing goes out before Send. What the secretary settles on its own is shown as "(done by the secretary)" with ↩️ Reopen. The owner talks to it in the Inbox topic (👀 and typing as elsewhere), e.g. "what did I miss since yesterday?" (it is told when the owner last wrote) or "ignore #random"; the brain relays the owner's triage wishes with `secretary-note`, each shown in **agent-communication**. **Rules** are one line each and only make triage quieter or louder; the secretary adds one only when the owner asks, quoting their words, and every rule change is posted in the **Rules** topic with **Undo** (or **Restore**), so the rules are one searchable log and the Inbox stays third-party only. A change counts as asked for only if the secretary is working on the very turn that answers the owner's own Inbox message (the orchestrator records what each run was handed, where and in the order it is sent, and counts each `result`; a run it did not see start counts as nobody's until it ends) and the change cites that message (at least three of its words, or most of a shorter one; for removals too); any other change is posted with a sound and a warning. At most 50 rules are active. `/secretary_reset` starts it on a fresh session (todos and rules stay; like `/brain_reset`, a session the stopped run reports late is ignored). The brain cannot direct it as a task (`send-to-task`, `stop-task`, `create-task --agent` refuse the fleet's own sessions). Escalations reach the brain through its persisted queue, counted under one lock. Settled todos are pruned with the rest of the history. In `dontAsk` mode `env`, `printenv`, `set`, `echo $VAR` and `/proc/self/environ` are all refused (checked against the real CLI), so the session's tokens cannot be printed; whether `--setting-sources ""` and `Bash(fleet agent:*)` survive a Windows `claude.cmd` batch wrapper is not checked: use `claude.exe` on a node that runs the secretary. Answers to the owner sound and start with "📋 Secretary:"; the **daily digest** (open todos first, then a short summary; at `FLEET_SECRETARY_DIGEST_HOUR` in `FLEET_TIMEZONE`, checked at start) is silent. |
| Brain administration | The owner can also set up the fleet by talking to the brain: projects (create, edit, secret folders, Slack channels), agents and bots (rename, unbind, remove; **not** add), nodes (settings, revoke) and secret folders (create, delete, unset keys). The web UI and the brain share one implementation (`admin.rs`). **Reads are free; every change is only a proposal**: an `admin_change` item in `needs you` with a summary written by the orchestrator (not the brain) and Approve / Reject buttons, also answerable on its web page. It runs once, on Approve, is audited as `owner (via brain)`, and its outcome goes back to the brain. Only the brain may call these tools. **Bot tokens, secret values and node tokens never pass through the brain**: reads show key names only, and for those the brain has the orchestrator send the owner a single-use login link to the right page. The brain never sees that link, so it cannot sign in and approve its own proposals. For the same reason the brain cannot have secret folders bound to its own project (its sessions would receive the values); a proposal that gives any project's agents secret folders carries a warning that the brain can direct those agents and so reach the values. In a node's Claude command the brain may only set or clear `--model` / `--fallback-model` (of the Claude program, never of a wrapper before it); the program and every other argument are the owner's, set on the web. A model set in the node's command wins over the fleet default. One change per proposal; the summary says what changes first and quotes free text (names, descriptions) last, and is never cut (a change too long to show in one message is refused). A Slack channel (`channel-add`/`channel-remove`) may be given by its name as well as its raw id, resolved against every conversation the secretary has already seen; an unknown or ambiguous name says so instead of guessing. A proposal stores the state it was written against and is not run if that state changed before the approval; it expires after 24 hours. **This gate is a boundary inside the orchestrator only**: on its machine the brain is a Claude session with a shell as the node's user, which can read other runs' `.env` files there, so the brain runs on a node that hosts no secret-bearing projects, and that user cannot read the deployment's `.env` or use Docker (see `deploy/README.md`). Redaction of secret values from agents' text guards against carelessness, not against a hostile brain. |
| Workflows | A standing automation the owner can trigger again later: periodically, on demand (writing into its topic), or both. Not a new kind of session or approval: **a workflow is a task whose topic is kept open.** The owner asks for one the same way as any task ("create a workflow to react on code-review pings", or "turn what we just did into one" while talking in an existing task's topic); the brain creates/reuses a task as usual, which goes through the ordinary plan-mode approval, and the agent finishes with `fleet agent workflow-finish` instead of `complete` once it is set up. The difference from `complete`: the topic is **not** closed, and the owner gets a control card (schedule presets — `every:15m/30m/1h/6h`, `daily:HH:MM`, or on-demand only — plus Pause/Resume and Delete, edited in place as they change). Writing into the topic already resumes the task through the existing follow-up machinery (reopen if needed, resume the stored session, or a fresh session that re-plans if the node was revoked) — nothing new there. Those later runs plan like any run, but their plans go to the workflow's **plan gate** (see Plan gate): a new workflow's plans wait for the owner until they tap 🔓 on its card, and from then on are approved for them and posted silently (the workflows that predate the gate start there). The only new mechanism is the periodic check: every 5 minutes, alongside reminders and retention, each enabled workflow whose schedule is due gets a synthetic message delivered the same way a follow-up is, and its due time advances only once that delivery succeeds. Disabling (Pause) only stops the periodic trigger; the owner can still write into the topic any time. No cron syntax, and no narrower tool access than any other task on that project: a feed-only workflow (no project work, just watching Slack/Google Chat) is just a brief that says so, not a new enforcement layer. A workflow task's own `feed_read`/`feed_search` still only sees its project's mapped Slack channels (like any task), so setting one up to react to Slack still needs `admin channel-add`; `workflow list` (brain and secretary) lists existing workflows, and a todo linked to one (`todo add --workflow <task-id>`) shows "▶️ Run workflow" instead of "🛠 Make task" — tapping it tells the brain to `send-to-task` that workflow rather than create a new one, so the secretary noticing a matching message (via a rule) and the owner's tap is how "watch a channel and nudge a workflow" works, without the secretary ever triggering anything itself. |
| Jira | Each project maps to **one Jira project key** (`BIOINS`, `DAP`) and, optionally, the **board** whose active sprint counts as "my sprint" (without one, every open sprint of the project does). **One credential normally serves the whole fleet**: an Atlassian email, API token and site URL in a secrets-manager folder (the existing `jira` preset's `JIRA_URL`/`JIRA_EMAIL`/`JIRA_API_TOKEN`), shared by default and overridable per project, so what differs per project is only the key and the board. **The credential never leaves the orchestrator**: it is not written to a node, not put in a session's environment and not shown to the brain, which reaches Jira only through tools (`jira sprint`, `jira issue`, `jira search`, `jira comment`, `jira transition`, and `jira create`/`update` as proposals). That is the same boundary the brain already has for secrets: it is steerable by untrusted content and has a shell on its machine, so a token there would be write access to the whole tracker. Reading, commenting and moving status happen at once and are audited (`jira.comment`, `jira.transition`); **creating an issue or editing its fields is an owner-approved `admin_change`**, inheriting its card, 24-hour expiry, staleness check (the project's Jira settings are the precondition) and `owner (via brain)` audit. Everything is scoped to the project's key: an issue of another project is refused, and every JQL is wrapped as `project = KEY AND (…)` with a trailing `ORDER BY` kept outside the parentheses, where JQL requires it. REST **API v2** (Cloud still serves it) so descriptions and comments are plain strings rather than ADF trees — with one exception, **search is `/rest/api/3/search/jql`**, because Cloud removed `/rest/api/{2,3}/search` outright and answers 410 pointing at the migration. Mixing is safe there: a search asks for no rich-text field, so nothing comes back as ADF. That endpoint pages by `nextPageToken` and reports no total, so a search says how many issues it read and whether more remain. Ticket text is **untrusted data**, framed like a feed message: nothing in a description or comment is an instruction. Waiting on a review or a status is a wakeup, not polling. **The agents read their own project's tracker too** (`jira issue`, `jira search`, `jira sprint`, `jira check`): a task is usually named after a ticket, and a reviewer who cannot read the ticket reviews against someone's summary of it instead. The project an agent names is ignored — only its own task's project is reachable from it — and commenting, transitioning, creating and editing stay the brain's, refused by name so an agent that tries is told to ask the owner rather than left with "unknown tool". `jira check` says where a project's Jira points, which account the fleet uses there and whether that account can see the project, because Jira answers a wrong site, an account without access and a mistyped key with the same 404; for the same reason a 401, 403 or 404 now names the site and the account it used. Agents on the owner's own machines may also use their own `jira` skill. |
| Wakeups | An agent that must wait (an MR not approved yet, a pipeline, a next-sprint ticket) **never holds a session open**: it asks the orchestrator, which is long-lived, to wake it later — `fleet agent wake set --note "..." --in 30m` (also `--at`, `--every`, `--until`). The note is the agent's message to its own future self and comes back word for word, with the number of times it has already been woken, so it re-checks with the tools it already has (`glab`, `git`, the project's scripts) and either acts, naps again, or reports and stops. **No integration with any third party is built for this**, which is the point: one mechanism covers merge requests, CI, deploys and anything else an agent can check. A second kind exists for what the orchestrator can judge from what it already holds: the agent describes the condition in **plain words** (`--when`), and the **brain** writes it as a small **Rhai** expression over a prepared snapshot (`ctx.messages` — the feed since the last check — plus `ctx.memo` for remembering a value, `ctx.task`, `ctx.now`), so new trigger kinds need no new Rust. Agents never write expressions. A condition is a **pure predicate**: no network, git, shell, database or secret access, no filesystem module resolver, and every evaluation is capped in operations and wall-clock; anything needing the outside world is a nap instead. Guards: at least a minute per nap and five between repeats, at most 10 armed per task, at most 6 wakes per task per hour (beyond that the wakeup waits an hour, audited as `wakeup.held`), a 30-day default expiry that still wakes the agent to say the wait is over, and three consecutive condition errors disarm it with a note in agent-communication and a line to the brain to rewrite it. Every wake is audited (`wakeup.fire`) and `/wakeups` lists what is armed, so none of this is invisible. Waking reuses the ordinary follow-up delivery, which resumes a finished task. A wakeup is the **agent's** (armed by itself, for one task); a workflow's schedule is the **owner's** (set on its card, running the whole workflow). |
| Plan gate | **Who approves an agent's plan is a setting of the work, not text in a prompt** (a rule that lives only in a brief is lost on the next session, restart or topic). Every new run plans first, and so does every run of a `done` task, which is what a workflow is once set up, so each tick and each message into its topic used to end in a plan card for a job the owner had already approved. Two values: `owner` (the plan card waits for their tap, as it always did) and `auto` (the agent still plans and the plan is still recorded as an item, but the orchestrator approves it through the same path a tap takes and posts it **silently** in the task's topic with the way back). It lives on the workflow (`workflows.plan_gate`: the workflows that existed before it became `auto`, and a new one starts at `owner` with the 🔓 button on its card, because an agent turns its own task into a workflow with `workflow_finish`, and setting one up, unasked or not, must not be what opens the gate) and on the project (`projects.plan_gate`, default `owner`, for tasks that are not workflows); a workflow's own setting wins. **Only the owner sets it**: the workflow card's button (🔒 Ask me for plans / 🔓 Approve plans automatically) and the project page in the web UI. There is deliberately no flag on `create_task`, `send_to_task` or `workflow_finish`, and it is not an `admin_change` the brain could propose, because the brain reads tickets and Slack and a gate it could open is a gate anything it reads could open. `auto` only ever answers `ExitPlanMode`; questions and tool permissions wait for the owner whatever it says, and so does a plan carrying one of the habits' stopper phrases (an open question, a blocker, TBD…) or one of a task already waiting on the owner for something else. Each approval is audited as `plan_gate.apply` under `owner (via plan gate)`. **What that does and does not buy, plainly** (as with habits): `auto` approves a plan whoever started the run — the owner writing into the topic, a schedule tick, the brain's `send_to_task` (a todo's "Run workflow" tap goes that way), a wakeup, another agent's message — so what the brain or an agent sends into an `auto` workflow is planned and done without a tap, and in an `auto` project so is every task the brain creates there. The record in the topic and its one-tap way back are what keep that visible. Approvals by the gate are marked on the item (`"by": "plan_gate"`), so the habits' reflection never mistakes them for the owner's own decisions, and the retrospective reads them as the gate's. A task created from a recurring job such as a code review that is not a workflow is a habit's case, not this one's. |
| Habits | The fleet watches **what the owner keeps doing** and offers to do it for them. Two kinds, one table (`habits`): a `decide` habit answers an item of a known shape the way they always answer it (today only a **plan**, approved — a plan's blast radius is one task), and a `do` habit makes a standing request of theirs on a schedule ("every Monday, summarise the weekend's chat") instead of waiting to be asked again. **The line that makes this safe: the brain proposes a habit in words, the owner approves it once, and the orchestrator then matches it in SQL.** Noticing is a judgment over text, so an LLM does it; acting is not, so an LLM never does. A habit is therefore born only as an ordinary owner-approved `admin_change` — with its card, 24-hour expiry, staleness check and audit. **What that does and does not buy, plainly:** the owner's tap is what decides that *this kind of work* may proceed without them; it is not a check on each task, because the brain creates tasks (including after reading a ticket or a Slack message) and a habit matches the project and the title's shape, never the brief. So a habit does widen what prompt injection into the brain could reach: within one project, one title shape, past the stoppers, ten times a day, visibly and reversibly. That trade is the feature, and the approval card says it in those words rather than implying a per-task gate that does not exist. It is why a habit may only ever *approve a plan* (never a permission prompt, an admin change, a reply to a third party or anything touching secrets), may not exist at all in the fleet's own project, and stands aside for good the first time the owner sends a plan of that shape back. Reflection runs once a day, costs nothing when there is nothing to see (plain SQL first: three or more decisions of one shape, all the same way, none sent back for changes, none already covered), and hands the brain the owner's own decisions and requests with the instruction to propose **at most one** habit or say nothing. A habit matches by project and the **shape of the task's title** (lowercased, digits collapsed: `review mr !#%`), not by agent, because it is a job that repeats. It never acts when anything says to ask: another blocking item of that task still open (the agent asked something itself), a plan naming a blocker, an open question, something unclear, a TBD or an assumption, any plan of that shape the owner has ever sent back for changes, or more than ten applications that day. Everything it does is visible and reversible — the plan is posted in the task's topic marked with the habit that approved it and a button that stops the task **and pauses the habit**, every application is audited as `owner (via habit n)` and counted on `/habits` and in the daily digest, and `/habits` plus a card in the Rules topic pause, resume or delete one. **A standing duty the owner states is a habit at once, never a memory** (retro P-4): "every day review two fresh MRs from #code-reviews", or "always keep the Jira status current — make it a rule", becomes a proposed `do` habit there and then — their words as `--why`, the duty and how to pick its candidates as the brief, a schedule, and the project it belongs to — rather than a note in the brain's memory that runs only when something happens to remind it and leaves no trace when it does not. (A secretary rule is not the place either: it only changes triage, and never makes work happen.) Triggers stay schedules; reacting to a channel is still a workflow plus a secretary rule. **And a habit keeps its own record**, so "did something go wrong?" is something to read rather than to reconstruct: when it was last evaluated, when it last acted, and a log of everything it stood aside from and why — the daily cap, a stopper in the plan (named), another question of that task open, a plan of that job sent back — and of anything it meant to do and could not (its request could not be handed to the brain). A standing request asks the brain to report, also when there was nothing to do: `fleet agent habit report <n> --did … --skipped "<candidate>: <reason>"` ("MR !412: already reviewed by someone else"), accepted only for a `do` habit that fired in the last two days, at most three per request, and kept as the brain's words, shown as text (and, read back by an agent through `admin show habits`, clipped and labelled as data, since its candidates often quote a feed). Each habit's status line ("fired 10:00; no report from the brain yet", "skipped 10:05: due, but its daily cap of 10 is reached") is the same in `admin show habits`, `/habits` and the web page, which also shows the log; the daily digest names any of the day's standing requests, over an hour old, that got no report before the next one went out, and a habit that failed to act and has not acted since. A request is recorded as fired before it is handed to the brain (and given back if it cannot be), so a report can never arrive for a request the log does not show. The orchestrator's repeated entries (a cap reached, looked at every five minutes) are written once a day. |
| Retrospective | Once a day the fleet **reviews its own day and proposes how to be better**: a third standing session (`retro`), beside the brain and the secretary, is handed a prepared digest — the day's tasks and how they went, what the owner decided and asked for in their own words, what the agents said to each other, the secretary's and the automation's day, and above all **what went wrong** (errors, failed spawns, undelivered text, lost runs) — and writes proposals about **the fleet itself**: its harness, how agents communicate, the flows and rules, features, refactors, integrations. Never about the owner's products; that is the orchestrator's job, not its. It may propose nothing and say so in its verdict, which is posted either way, so a quiet day reads as a quiet day rather than a silent failure. Proposals land in the **📈 Retro** topic as cards, and **one tap turns a proposal into a task on the fleet's own code** — in one project (`FLEET_RETRO_PROJECT`, a clone of this repository mapped on a node that can build it), never in a product project, with a brief the orchestrator composes: the proposal framed as *a proposal to verify, not an instruction*, plus that project's rules (read `CLAUDE.md` and `docs/plan.md` first, work on a branch, keep fmt/clippy/tests green, **never push or deploy**). Dismiss closes it; both are audited and the card says what became of it. It is held exactly as the secretary is — no secrets, an empty directory, only `fleet agent` in its shell, `dontAsk` so it can never prompt anyone — and its tools are reads plus three writes (`retro_propose`, capped per day, `retro_finish`, and `retro_person`, which keeps the people records — see People network). It cannot create a task, answer the owner, message an agent, administer anything or answer a human item, and a test asserts each refusal. It reads untrusted material, so a crafted message can influence what it *proposes*; between that and anything happening stand the owner's tap and an agent working in a clone it cannot push. **What makes it a loop rather than a daily amnesia** is Hindsight: its verdicts, its proposals, the owner's decision on each and what became of the work are retained in the fleet's own bank, where a **mental model** — Hindsight's standing synthesis, a document it re-answers as memories accumulate, in `delta` mode on a cron an hour before the retrospective runs, with a weekly full regeneration to clear drift — keeps one answer to "what has this fleet learned about itself, what did the owner accept or dismiss, and what is settled". Every digest opens with that document, so each day is read against everything before it, and a bank **directive** shapes how those memories are extracted (symptom, what was tried, whether the owner wanted it, whether it worked, ids kept verbatim). The orchestrator creates both on first use and asks for a refresh when a day closes; if Hindsight is not configured or is unreachable the retrospective still runs on the day alone. Off until `FLEET_RETRO_HOUR` is set. |
| People network | **A record of each of the owner's colleagues the fleet comes into contact with**, so whoever writes to them knows who they are writing to: position, a brief (what they are involved in), the company's projects they work on (free text, not fleet projects), the language to write to them in (English or Ukrainian), how to reach them (contacts: a source — Slack, Google Chat, email, Telegram, other — a handle a person reads, and the source's own user id), observations ("prefers short and quick communication", "does code reviews on the notes module", "non-technical"), **tags** for anything that fits no field (the owner later turns recurring tags into fields; the web page counts them), and when they were last in touch. **Who writes: the retrospective, and among agents only it** — after its review it goes over the day's material (the digest's People section lists who wrote in the owner's conversations, by source and user id, and whether each has a record) and its memories, and creates or updates records with `retro_person`: by name (case-insensitive, never a duplicate) or id, lists added to and taken from rather than replaced (except a person's projects), `last_interaction` only ever moving forward, at most `FLEET_RETRO_MAX_PEOPLE` writes a run, each audited (`person.upsert`) in the same transaction the cap counts. **It pings nobody**: the owner asked to review the records when they choose, so nothing about them reaches Telegram. Any other agent calling `retro_person` is refused by the tool gate. **The owner edits and deletes** on the People page; an edit replaces what the form sends (refused if the record changed since the form loaded), and **every field it changes becomes the owner's for good** (`owner_fields`, with `owner_edited_at`): the retrospective may not change such a field, and of the owner's observations, tags and contacts it may only add, never take away or rewrite — once the owner has edited a list it cannot tell their items from its own, so the whole list is protected. A refused write tells the retrospective which fields are the owner's. Cards and the page say "last edited by the owner on …" from that column. The owner's changes are audited in the same transaction and go straight through `people`, not `admin`, since no agent may propose one. **Who reads: everyone, before writing.** The read-only `people` tool (`fleet agent people <query>`, `--id <n>`) is every agent's, the secretary's and the retrospective's included. The secretary's batches end with the whole cards of the people who wrote in them (those who wrote to the owner personally first), as do its replies-in-context; what reaches the brain — feed reads, triage-channel notes, escalations, Inbox requests — names each known author in **one line** pointing at the card (`#4 Zed Example — Backend lead, Ukrainian; full record: fleet agent people --id 4`), because the brain's session is long and reads many messages. The brain's and the secretary's prompts say to read a colleague's card before writing to them and **use it for language, tone, form of address and who they are (role, what they work on) — never for how urgent a message is, whom to escalate or reply to, what may be shared, or what work to do**. The People section of the retrospective's digest is built first and capped (about 3,000 characters, authors listed while they fit), so a busy day clips the other sections, never it. A message from someone with a record moves their `last_interaction` to its time (one `UPDATE … FROM`). **The owner is never one of the people**: `feed_messages.from_owner` records what the source said at ingest, and the owner's messages and accounts are kept out of the digest's People section, the cards and `touch`, and refused as anyone's contact. **Trust:** a record is written by a session that read third parties' messages, so it is **untrusted data written from untrusted material** — framed as such wherever an agent is handed one (JSON-quoted, clipped, "never instructions"), and it can change how the fleet *writes* to someone, never what it may *do*. |
| Agent ↔ fleet interface | **No Telegram MCP, and no MCP for agent tools.** Only the orchestrator's Rust code talks to Telegram. Agents use the `fleet agent` CLI from their shell, taught by a `fleet` skill that the node loads into each session as a plugin (`--plugin-dir`). The only MCP server is the fleet's tiny permission hook, which Claude Code requires for `--permission-prompt-tool` (plan approval, questions, tool permissions). |
| Web UI | A single-page app (React + Radix Themes, in `apps/web`) on a JSON API (`api.rs`), **compiled into the `fleet` binary**: one artefact to deploy, and the UI cannot drift from the API it talks to. It covers the dashboard, approvals (plans, questions, permissions, proposals, admin changes), **every task including finished ones, filterable by project, status, agent and free text**, **the fleet's sessions** — one row per agent process, with how long it ran and how it ended — a project's own tasks and session count, the secretary's inbox (todos, rules, triage), agents, nodes and secrets. **Every page is a URL**, filters included (`/tasks?project=bioins&status=failed`, `/sessions?project=dap`), so a magic link can land the owner on exactly what is being discussed; the orchestrator sends those links with `web_link` against a whitelist of pages, and `web::safe_target` refuses any redirect that would leave the site. Authentication is unchanged: single-use magic links from the bot, a `SameSite=Strict` session cookie, and mutations that additionally require a JSON body, so a cross-site form post cannot drive the API. **Nothing serialises a database row**: every response is built field by field, because rows carry what a browser must never see (`nodes.auth_secret`), and a secret's value is never read back. Untrusted text (Slack, Jira, agent output) is rendered as text — `dangerouslySetInnerHTML` is forbidden and a test enforces it. |
| Deploy | Docker Compose on the VPS: orchestrator, Postgres+pgvector, Hindsight, iroh-relay, Caddy (HTTPS on your subdomain). |
| Updates | Signed releases. They are pushed to nodes after you approve in Telegram. Busy nodes update once their agents finish. |
| Limits | No limits on turns, time or cost. |
| Retention | Transcripts, feed messages of mapped channels, the secretary's triage log and audit logs are kept 90 days (`FLEET_RETENTION_DAYS`); messages of every other conversation the owner is in are kept `FLEET_FEED_RETENTION_DAYS` (default 90). Memories and task records are kept forever. Nightly Postgres backups. |

## Architecture

```
                         ┌───────────────────────── VPS (docker compose) ─────────────────────────┐
 You ── Telegram group ──┤ fleet orchestrator                                                    │

 Slack ◄─ poll (user tk)─┤  ├─ feeds: Source trait → SlackSource (more later)                    │
 Browser ── HTTPS ───────┤  ├─ web: axum + htmx (plan pages, projects/secrets, nodes/agents)     │
                         │  ├─ router/bus, scheduler, human queue, secrets vault (age-encrypted) │
                         │  ├─ brain: Claude Code session on the VPS node (`fleet agent` CLI)   │
                         │  └─ net: iroh endpoint (ALPN fleet/1)                                 │
                         │ postgres+pgvector · hindsight · iroh-relay · caddy · fleet node (VPS) │
                         └──────────────────────────────▲─────────────────────────────────────────┘
                                                        │ iroh QUIC (key-pinned, NAT traversal)
                     ┌──────────────────────────────────┴──────────────┐
               fleet node (Windows service)                      fleet node (…)
                ├─ agent supervisor → claude -p (stream-json) per agent session
                ├─ loopback IPC (token per agent) ← `fleet agent ...` CLI + `fleet mcp` permission hook
                ├─ secrets drop: <data>/secrets/<task>/*.env (user-only ACL, wiped at task end)
                └─ updater, project mappings, session archive upload
```

### Rust workspace (new repo)
- `crates/proto`: versioned wire types (serde + postcard). Every message is wrapped in an envelope `{id, ack_of, ts, kind}`.
- `crates/net`: the iroh endpoint, ALPN `fleet/1`, length-prefixed frames, reconnect with backoff, and a durable outbox that resends until the other side confirms receipt.
- `crates/orchestrator`: state (sqlx + Postgres, migrations), scheduler, message router, human queue, Telegram, feeds, web, vault, brain supervisor.
- `crates/node`: the Claude runner, agent supervisor, IPC server, secrets drop, updater, Windows service (`windows-service`) / systemd.
- `crates/node` also holds the `fleet agent` CLI, the `fleet` skill plugin and the `fleet mcp` permission hook (a hand-written stdio JSON-RPC server, no MCP SDK).
- `crates/cli` → a single binary `fleet` with subcommands: `orchestrator | node | mcp | invite | join | secret | project …`.
- `deploy/`: `docker-compose.yml`, Caddyfile, iroh-relay config, Hindsight config.

## Key flows

1. **Joining a node:**
   - Run `fleet invite` on the VPS. It produces a one-time ticket that contains the orchestrator's iroh address and an expiring secret.
   - Run `fleet join <ticket>` on the PC. Its key is added to the allowlist, and it installs and starts itself as a service.
   - The node's Claude command and auth are then set in the web UI.
2. **Mapping a project:** create the project once in the web UI (tracker preset, secret bindings, Slack channels). On a node, run `fleet project map <slug> <path>` or use the web UI.
   - On Windows, the tray app (`apps/tray`, Tauri + Svelte) does the same from a window. The node starts it (`fleet-tray.exe` next to `fleet.exe`, unless `FLEET_NO_TRAY=1`) and it exits with the node; one tray per user, serving one data directory.
   - The orchestrator sends every node the project list (`Body::ProjectList`, protocol 3) on connect and after each project create or edit. The node writes it, its link state and its pid to `status.json`; the tray offers those slugs in a dropdown and flags mappings the orchestrator does not know.
   - The tray edits only `projects` in `node.json`. Every writer of `node.json` (the node saving pushed settings, `fleet project map`, the tray) loads, changes and saves it while holding `node.json.lock`, an OS file lock, so one writer's change is not saved over by another's. The lock is advisory: a hand edit or an older binary that does not take it can still race. Saves are atomic renames from a per-writer temp file, so readers never see a half-written file. The node picks up mapping changes within 5 s.
   - `status.json` carries the node's pid and that process's start time, so the tray does not take a later process that reused the pid for the node.
3. **"do X" in Telegram (General, or a project topic):**
   - The orchestrator bot receives it and passes it to the **brain** session. The brain:
     - looks up memory in Hindsight;
     - lists projects and agents;
     - decides the project and ticket (it can create a tracker issue through your skills or MCP if the project's rules say so);
     - picks an existing specialist on that project (by similarity of past work) or creates a new agent with a free bot;
     - calls `create_task(...)` with a brief.
   - The orchestrator then creates the topic `{proj}-{ticket}` and sends `SpawnAgent` to the node that has the project (preferring the agent's usual host). If that node is offline, the task waits in a queue and you get a note in `needs you`.
4. **Agent run on the node:**
   - The node writes the secrets `.env` files.
   - It runs the configured start command with `-p --input-format stream-json --output-format stream-json --verbose --model opus --permission-mode plan --mcp-config <fleet permission hook> --permission-prompt-tool mcp__fleet__permission --plugin-dir <fleet skill> --append-system-prompt-file <role + brief + worktree/secrets/milestone instructions>`, or adds `--resume <session_id>` when resuming.
   - It streams events back to the orchestrator, which saves the transcript.
5. **Plan approval:**
   - The agent calls `ExitPlanMode`. It goes to the `fleet.permission` tool, which turns it into a **plan page**, along with any `AskUserQuestion` calls made during planning.
   - You get a magic link in the task topic and in `needs you`.
   - On the page you answer the questions and approve, or send feedback.
   - The tool returns allow (with the answers in `updatedInput`), and the session switches to `auto` mode.
   - **An interruption never skips the approval.** A task whose plan has not been approved (`tasks.plan_approved`, cleared when a run starts in plan mode and set on approval) is resumed in plan mode again. That covers a run lost to a node restart, a crash or an idle close, and the task being queued, stopped or failed meanwhile. The agent re-presents its plan, and the owner approves it as before.
   - **A text for a run that is gone is redelivered, not lost.** The node hands it back (`Undelivered`), and the orchestrator resumes the session with it, or keeps it in the task's queue for its next run. Both events stay in the transcript: `undelivered`, then `redelivered` with the outcome. The retrospective's digest lists these texts with that outcome rather than as failures.
6. **Execution:**
   - The agent calls `fleet.milestones_set([...])` once and `fleet.milestone_done(i)` as it goes, which edits the checklist message.
   - `fleet.ask_human(question, options?, blocking)` creates an item in `{proj} · needs you` (or `fyi`) with buttons, and accepts a free-text reply to that message. The answer goes back into the session.
   - **One open question per task.** An agent asking again retires what it asked before (it is running, so it is not blocked on a question of its own: the earlier one is the same thing in older words, or a call its session abandoned), and a task that finishes closes whatever it left open. A retired item shows its outcome on every copy, and a tool call still blocked on it is let go with a denial. Nothing waits on the owner for a question nobody is listening for any more.
   - **A message from the owner is answered in the topic, not only in the session.** An agent's own text goes nowhere: the stream is recorded as the task's transcript (visible in the web UI) and never posted to Telegram, so an agent that answers the owner by just writing an answer leaves them looking at a silent topic. The agents are told to answer with `fleet agent post` (or `ask`), and when a turn that was started by the owner's message ends without anything having reached them — no post, no question, no completion, no card — the orchestrator posts what the agent last said, once, with a sound. An answer the owner cannot see is the same as no answer.
   - `fleet.ask_agent` / `fleet.post` send messages to other agents through the message bus (stored, confirmed on receipt, with a hop limit to stop loops). A short copy of an agent-to-agent message appears in **agent-communication** (as the sender's bot, labelled with both names and the task), not in the task's own topic; `post` stays in the task's topic, which is that agent's work.
   - At the end, `fleet agent complete` posts a summary and closes the topic. The brain is told automatically whenever a task ends: done (with the agent's summary, JSON-quoted as untrusted data, after the project's secret values are redacted from it), stopped, failed, interrupted (its node restarted or lost the run), or unable to start. Only the task's current run counts, and never the brain's own. The brain stays quiet unless a follow-up is needed or the owner asked to hear about it. The session then ends (freeing the node) and is resumed for follow-ups. The agent stores durable facts with `fleet agent memory retain`.
   - **The topic is deleted once it goes quiet** (an hour by default, `FLEET_TOPIC_DELETE_AFTER_MINUTES=0` to keep them), so the forum shows what is going on rather than everything that ever did. Only a task's own topic, never a standing one, never while something of that task still waits on the owner, and only when Telegram confirms; a task picked up again gets a topic named as before. The bot needs the *Delete messages* right, and says so once if it does not have it. What was said in a deleted topic is still in the task's transcript, its sessions and the web UI.
7. **Follow-up on old work:** the brain recognises the task or agent. The topic is reopened, and the stored session is resumed with `--resume` on the same node and folder. Session JSONL files are archived on the VPS so a session can be restored if a node is rebuilt. If the session's node has been revoked, the session cannot be resumed: the next message starts a fresh session on another node with the project, which gets the task's brief before the message and **starts in plan mode again** (the agent re-plans and the owner approves the plan again). That is deliberate: a fresh session has none of the earlier context, so it should not act before a plan is approved.
8. **Slack (Socket Mode for every conversation; or, with the user token only, polling of mapped channels):**
   - The adapter keeps a cursor per channel (the last `ts` seen) and polls each mapped channel's history. It also checks threads that are still active (`conversations.replies`) for a while. Busy channels are polled more often and quiet ones less. Every request goes through one rate-limit budget per token.
   - The adapter stores each message (as untrusted data) and mirrors it into the project's feed topic. If the channel is busy, messages are batched into digests to stay within Telegram limits.
   - Agents read Slack through `feed_read` / `feed_search`.
   - The brain may post a **task proposal** or a **reply proposal** in `needs you`. A reply is sent to Slack only after you approve it.
   - Every message outside a triage channel (and not written by the owner) also goes to the **secretary** (see Decisions): batched, framed untrusted, triaged into ignore / note / todo / escalate. Its todos and rule changes appear in the 📋 Inbox topic and on `/inbox`.
9. **Reminders:** open `needs you` items are re-pinged after 2 hours, never auto-answered. `/queue` lists open items across projects.

### `fleet agent` commands (taught by the `fleet` skill)
`milestones`, `done`, `skip` (with `--reason`), `ask` (with `--option` and `--fyi`), `tell`, `post` (silent; `--notify` for sound, once per task per 10 minutes), `complete`, `wake set`/`list`/`cancel` (waiting without a session), `workflow-finish` (with `--schedule`; like `complete` but keeps the topic open and triggerable, see Decisions), `feed read`/`search`, `memory retain`/`recall`/`reflect`/`banks` (`--bank`, `--shared`). Secrets are read with `fleet secret get`/`exec`.

The brain additionally gets `projects`, `agents`, `tasks`, `create-task` (with optional `--model`/`--effort`), `send-to-task`, `stop-task`, `propose-task`, `propose-reply`, `reply`, and `admin ...`: `admin show <what>` (reads) and one proposal command per change (`project-create`, `project-edit`, `project-bind`/`unbind`, `channel-add`/`remove`, `agent-rename`/`unbind`/`remove`/`set` (model and effort), `bot-remove`, `node-set`, `node-revoke`, `folder-create`/`delete`, `secret-unset`), plus `admin link <page>` to send the owner a login link, and `secretary-note` to pass the owner's triage wishes to the secretary.

The secretary gets only its own commands: `triage ignore|note <ref>...`, `todo add`/`list`/`update`, `escalate --summary ... --source <ref>`, `digest post`, `rule add --text ... --because "<owner's words>"`/`list`/`remove`, plus `feed read` (`--ref`, `--conversation`)/`search` over every conversation and `memory` in its own banks. Long text goes in a heredoc (`--text - <<'EOF'`); `$(...)`, `VAR=...` prefixes and pipes into `fleet agent` are refused.

### Telegram details
- **Orchestrator bot:**
  - is a group admin with `can_manage_topics`;
  - has privacy mode off, so it reads everything;
  - creates and closes topics and routes your messages.
- **Agent bots** only send messages, and are polled only for presses on their buttons.
- Each bot has its own send queue with a rate limiter (about 20 messages a minute per group).
- Checklists:
  - The plan is native checklists (`sendChecklist`). These may only be available to business accounts, which the phase 0 spike checks.
  - The fallback is a single message with ☐/☑ lines that gets edited.

## Verification

- **Automated tests (CI):**
  - a fake `claude` binary that emits scripted stream-json, including ExitPlanMode and AskUserQuestion permission calls;
  - a mock Telegram Bot API server;
  - a mock Slack.
- **Integration tests:** the orchestrator and two nodes run in one process on loopback iroh, with Postgres via testcontainers. Each flow from "Key flows" is an end-to-end scenario test.
- **Failure-injection tests:** randomly drop iroh connections and kill node or Claude processes, then check that every message arrives exactly once and every session resumes.
- **Manual acceptance on real hosts:** the VPS plus your Windows PC with both auth modes. Run the phase exit scenarios above in a real Telegram group with a real Slack workspace.
- **Security checks:**
  - an unknown Telegram user is ignored;
  - an unknown iroh key is refused;
  - an expired magic link is rejected;
  - no secret value appears in transcripts or logs (grep the archived transcripts in CI scenarios).
